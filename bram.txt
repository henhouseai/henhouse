Systems that behave like BitTorrent plus structured writes are basically in the space of:

DHT-backed storage layers (Kademlia variants).

CRDT-based replicated data structures.

Content-addressed data stores (IPFS-style).

Permission models layered on top of a decentralized substrate.

Below is a clean map of the building blocks and what choices matter.

1. Core substrate: DHT (Kademlia or variant)
A DHT gives you:

Key ? location mapping without a central server.

Nodes responsible for key ranges (or buckets).

O(log N) lookup.

BitTorrent’s “Mainline DHT” and IPFS’s routing layer both derive from Kademlia.
If the goal is “store objects across the network and fetch them by an ID,” this is the correct base.

Two choices:

Location-based keys – keys represent logical items, values are stored at responsible nodes.

Content-addressed keys – keys are a hash of the data. No node “owns” a logical slot; nodes just host chunks whose hash falls in their range. This scales better and avoids conflicts.

If you want BitTorrent-like availability and deduplication, content-addressed is usually the right choice.

2. What you need for mutable state
DHTs are naturally immutable. Writes must be layered on top.
The standard approaches:

A. Mutable pointers to immutable blobs
You maintain a signed record:

public_key ? {sequence_number, content_hash, signature}
Anyone can fetch the mutable pointer, verify the signature, and retrieve the referenced blob.

This is how IPNS (IPFS’s mutable namespace) works.
Your “ownership token” becomes the private key controlling the mutable pointer.

B. CRDTs (Conflict-Free Replicated Data Types)
If you want truly distributed writes without a single writer key, a CRDT ensures all replicas converge without coordination.

Examples:

OR-Map

LWW-Register

RGA / sequence CRDT

G-Counter / PN-Counter

CRDTs don’t require consensus and don’t require a single “owner,” but they also don’t give strong authorization unless you combine them with signatures per operation.

3. “Ownership” or write-control
You layer authorization on top of your mutation system.

Option 1: Cryptographic ownership
Writes must be signed by a specific private key.

The public key is the authoritative identity.

You can rotate keys by having the old key sign a pointer to a new key.

This is the simplest model.
This is basically “token = private key.”

Option 2: Multi-sig policies
For collaborative control:

A CRDT where each update carries a signature.

Each replica verifies signatures against a policy list.

Policies themselves are stored in a signable CRDT.

Option 3: Token-based capability system
Capability tokens are separate signed objects that grant rights.
Nodes enforce rights by checking the capability presented with each write.

4. Data placement (availability, redundancy)
Options:

A. Replication factor K
Each chunk stored at K nodes nearest to its hash.
Typical values: 5–20 depending on network churn.

B. Erasure coding
Instead of K full replicas, you break data into N shards, with any M reconstructing the original.
More efficient, common in decentralized storage networks (Storj, Filecoin).

C. Opportunistic caching
BitTorrent-style: nodes cache chunks they serve.
Improves read performance and robustness.

5. Consistency goals
Because this is decentralized, you usually accept:

Eventual consistency for reads.

Strong integrity but weak ordering for writes.

Optional per-object linearizability under single-writer-key models.

If you need coordinated agreement on a global sequence of writes, you need consensus (raft/paxos), but that gives up decentralization.

6. Real-world analogs
Useful comparisons:

IPFS + IPNS + libp2p DHT
Closest to what you’re describing if you combine with CRDTs (IPFS supports CRDT-based datastores like OrbitDB).

Hypercore / Hyperswarm (BitTorrent-like routing + append-only logs)
Each mutable feed is owned by a keypair; perfect for distributed DB logs.

BitTorrent + BEP 44 mutable items
Allows storing a mutable value in the DHT, signed by a keypair.

Secure Scuttlebutt (append-only logs signed by each user)
Not hash-lookup-based, but demonstrates decentralized, append-only, signed data structures across untrusted peers.
