# Chapter 9: HTTP/NGINX Configuration

## Overview

Configure the web server to serve your Henhouse installation. This is a two-phase process: HTTP-only first (for SSL certificate verification), then HTTPS with SSL.

## Prerequisites

Before configuring NGINX, ensure you have:

1. **Chapter 8**: File deployment completed (NGINX config is generated from deployed code)
2. **Chapter 1**: DNS configured and pointing to your server
3. **Chapter 3**: SSL certificates ready (for Phase B)

## Phase A: HTTP-Only Configuration

If you're setting up a new domain, start with HTTP-only to allow SSL certificate verification:

```bash
# Configure HTTP/NGINX (HTTP-only, for SSL certificate setup)
sudo {hen_script_name} http-deploy -domain yourdomain.com
```

**What this does**:
- Creates NGINX configuration for your domain
- Sets up server blocks for main domain, admin, and panel subdomains
- Includes ACME challenge location for Let's Encrypt certificate verification
- Allows SSL certificate authority to verify your domain by uploading a file and checking it
- Writes config to `/etc/nginx/sites-available/{domain}`
- Creates symlink in `/etc/nginx/sites-enabled/{domain}`
- Tests configuration with `nginx -t` before reloading
- Falls back to restart if reload fails
- Cleans up bad config if test fails

**Why HTTP first?**
- Let's Encrypt needs to verify domain ownership via HTTP
- ACME challenges must be accessible on port 80
- Once SSL certificate is issued, proceed to Phase B

## Phase B: HTTPS Configuration

After SSL certificates are installed (typically via Let's Encrypt):

```bash
# Configure HTTPS/NGINX with SSL certificates
sudo {hen_script_name} http-deploy-ssl -domain yourdomain.com
```

**What this does**:
- Upgrades HTTP configuration to HTTPS
- Configures NGINX with SSL certificates
- Sets up HTTP-to-HTTPS redirects
- Maintains ACME challenge location for certificate renewal
- **Overwrites** existing HTTP config (doesn't merge)
- Optional `-cert_path` parameter (defaults to `/etc/letsencrypt/live/{domain}`)
- Uses certificate files: `fullchain.pem` and `privkey.pem`

**Requirements**:
- SSL certificates must be installed (see Chapter 3)
- Let's Encrypt certificates should be in `/etc/letsencrypt/live/{domain}/`
- NGINX must be installed and running (see Chapter 1)

## Technical Details: NGINX Configuration Architecture

NGINX serves as a reverse proxy in front of Flask applications:

- **Main domain** (e.g., `example.com`, `www.example.com`): Proxies to guest tier Flask (port 5001)
- **Admin subdomain** (`admin.example.com`): Proxies to admin tier Flask (port 5003) with HTTP Basic Auth
- **Panel subdomain** (`panel.example.com`): Proxies to root tier Flask (port 5004) with HTTP Basic Auth

**Configuration Files**:
- **Location**: `/etc/nginx/sites-available/{domain}`
- **Symlink**: `/etc/nginx/sites-enabled/{domain}` → `sites-available/{domain}`
- **Deployment Marker**: Config files include "Generated by henhouse deploy-http system" or "Generated by henhouse deploy-ssl system" markers

The HTTP deployment system (`hh/deploy/http/http_deploy.py` and `http_deploy_ssl.py`) generates NGINX configuration from deployed code and whitelists.

## Technical Details: NGINX Configuration Helpers

The NGINX configuration system (`hh/deploy/http/nginx_config_helpers.py`) provides helper functions for generating configuration blocks:

**Key Functions**:
- **`get_server_configs(domain, project_name)`**: Returns server configuration definitions
  - Detects Flask ports from deployed app files
  - Returns 3 server configs: main (guest), admin, panel (root)
  - Falls back to default ports (5001, 5002, 5003, 5004) if files not found

- **`generate_server_block(...)`**: Generates HTTP server block
  - Server names, port, static locations, label
  - Includes security headers, rate limiting, hidden file blocking
  - Adds HTTP Basic Auth for admin/panel subdomains
  - Flask proxy configuration

- **`generate_https_server_block(...)`**: Generates HTTPS server block
  - Same as HTTP block plus SSL certificate configuration
  - HTTP/2 enabled
  - HSTS header included

- **`generate_http_redirect_block(all_domains)`**: Generates HTTP-to-HTTPS redirect
  - Listens on port 80
  - Returns 301 redirect to HTTPS
  - Automatically includes `db.{domain}` and `cache.{domain}` subdomains for ACME challenges

- **`get_security_headers()`**: Standard security headers for HTTP
- **`get_security_headers_ssl()`**: Security headers for HTTPS (includes HSTS)
- **`get_rate_limiting()`**: Rate limiting configuration
- **`get_block_hidden_files()`**: Blocks hidden files (allows `.well-known` for Let's Encrypt)
- **`get_auth_block(project_name, tier)`**: HTTP Basic Auth configuration
  - Admin tier: uses `/var/www/.htpasswd_admin`
  - Root tier: uses `/var/www/.htpasswd_panel`
- **`get_flask_proxy_block(port)`**: Flask reverse proxy configuration
  - Proxy to `http://127.0.0.1:{port}`
  - Sets proxy headers (Host, X-Real-IP, X-Forwarded-For, X-Forwarded-Proto)
  - 50MB max body size for file uploads

- **`detect_flask_ports(project_name)`**: Detects actual Flask ports from deployed app files
  - Reads `{project_name}_{tier}.py` files
  - Extracts port number from `port = XXXX` pattern
  - Falls back to defaults if files not found
  - This ensures NGINX proxies to the correct Flask ports even if port configuration changes

## Technical Details: NGINX Static File Serving

The NGINX static file whitelist system (`hh/deploy/http/nginx_whitelist.py`) generates location blocks for static file serving:

**Process**:
1. **Collect Static Directories**:
   - From `JS_WHITELIST`: adds `site/js/`
   - From `CSS_WHITELIST`: adds `site/css/`
   - From `MISC_WHITELIST`: adds `site/`, `site/css/`, or `site/js/` based on path
   - From `CONTEXT_WHITELIST`: adds context folders (e.g., `context/`, `planning/`)

2. **Generate Location Blocks**:
   - Always includes `/srv/images/{project_name}/` (for image storage)
   - Generates location blocks for each static directory
   - Each block:
     - Maps URL path to filesystem alias
     - Sets `expires off` and `Cache-Control: no-cache, no-store, must-revalidate`
     - Prevents caching of static files
   - Returns config string and summary counts (JS files, CSS files, misc files, context folders)

**Static File Locations**:
- `/site/js/` → `/srv/{project_name}/site/js/`
- `/site/css/` → `/srv/{project_name}/site/css/`
- `/site/` → `/srv/{project_name}/site/` (for misc files like favicon.ico)
- `/context/` → `/srv/{project_name}/context/` (for context documentation)
- `/srv/images/` → `/srv/images/{project_name}/` (for image storage)

**Files**: Files are served via Flask routes for gated access:
- `/file/<id>` - Shows file page (via `show-file` action)
- `/file/<id>/download` - Downloads file (via download backend)

## Technical Details: Security Features

**Security Headers**:
- **X-Frame-Options**: `SAMEORIGIN` (prevents clickjacking)
- **X-Content-Type-Options**: `nosniff` (prevents MIME sniffing)
- **X-XSS-Protection**: `1; mode=block` (XSS protection)
- **Referrer-Policy**: `strict-origin-when-cross-origin`
- **Strict-Transport-Security** (HTTPS only): `max-age=31536000; includeSubDomains` (HSTS)

**Rate Limiting**:
- **General zone**: For main site (guest tier)
- **Admin zone**: For admin and panel subdomains
- **Burst**: 20 for general, 100 for admin
- **No delay**: Immediate enforcement

**Hidden File Blocking**:
- Blocks all hidden files (starting with `.`)
- **Exception**: Allows `.well-known/acme-challenge/` for Let's Encrypt certificate validation
- Prevents access to sensitive files like `.htpasswd`, `.env`, etc.

## Verification

After configuring NGINX:

1. **Test HTTP access**: Open `http://yourdomain.com` in a browser
2. **Test HTTPS redirect**: HTTP should redirect to HTTPS
3. **Test subdomains**: 
   - `http://admin.yourdomain.com` (requires HTTP Basic Auth)
   - `http://panel.yourdomain.com` (requires HTTP Basic Auth)
4. **Check NGINX status**: `sudo systemctl status nginx`
5. **Test NGINX config**: `sudo nginx -t`

## Troubleshooting

### NGINX Configuration Test Fails

**Problem**: `nginx -t` fails or NGINX won't start

**Solutions**:
1. Check NGINX config syntax: `sudo nginx -t`
2. Review error messages in NGINX logs: `sudo tail -f /var/log/nginx/error.log`
3. Verify SSL certificate paths are correct
4. Check file permissions on certificate files

### SSL Certificate Not Found

**Problem**: HTTPS deployment fails because certificates aren't found

**Solutions**:
1. Verify certificates exist: `ls -la /etc/letsencrypt/live/{domain}/`
2. Check certificate paths in NGINX config
3. Ensure Let's Encrypt certificates are installed (see Chapter 3)
4. Run HTTP deployment first to allow certificate verification

### HTTP Not Redirecting to HTTPS

**Problem**: HTTP doesn't redirect to HTTPS

**Solutions**:
1. Verify HTTPS deployment completed: `sudo {hen_script_name} http-deploy-ssl -domain yourdomain.com`
2. Check NGINX config includes redirect block
3. Reload NGINX: `sudo systemctl reload nginx`
4. Check NGINX error logs for issues

### ACME Challenges Fail

**Problem**: Let's Encrypt certificate verification fails

**Solutions**:
1. Verify HTTP deployment includes ACME challenge location
2. Check `/var/www/html/.well-known/acme-challenge/` is accessible
3. Ensure NGINX serves ACME challenges on port 80
4. Verify DNS points to your server

## Removing HTTP/NGINX Configuration

To remove NGINX configuration for a domain:

```bash
# Remove HTTP/NGINX configuration
sudo {hen_script_name} http-remove -domain yourdomain.com
```

**What this does**:
- Validates that the domain was deployed by Henhouse (checks installation manifest)
- Only removes sites that were deployed by Henhouse (safety feature)
- Removes symlink from `/etc/nginx/sites-enabled/{domain}`
- Removes config file from `/etc/nginx/sites-available/{domain}`
- Tests NGINX configuration
- Reloads NGINX

**Safety Feature**: The command checks the installation manifest (`manifest_sites` section in install config) to verify the site was deployed by Henhouse. This prevents accidental deletion of manually configured sites.

**Note**: You must remove all HTTP/NGINX sites before running uninstall (see Chapter 17).

## Technical Details: HTTP Status Command

The `http-status` command scans and reports NGINX configuration status:

**Process Flow**:
1. **Scan NGINX Sites**: Scans `/etc/nginx/sites-available` for all config files, checks `/etc/nginx/sites-enabled` for enabled sites (symlinks)
2. **Detect Configuration**: Reads each config file to detect:
   - Henhouse marker: "Generated by henhouse deploy-http system" or "Generated by henhouse deploy-ssl system"
   - SSL presence: Checks for `ssl_certificate`, `listen 443`, or `ssl http2`
3. **Categorize Sites**:
   - **active_henhouse**: Enabled + has Henhouse marker
   - **available_henhouse**: Not enabled + has Henhouse marker
   - **active_other**: Enabled + no marker (manually configured)
   - **available_other**: Not enabled + no marker
4. **Check NGINX Service**: Checks if NGINX service is active via `systemctl is-active nginx`
5. **Return Summary**: Returns categorized sites with SSL status and deployment stage (Stage 1 = HTTP only, Stage 2 = HTTPS)

This helps you see which sites are deployed by Henhouse vs manually configured, and their current SSL status.

## Technical Details: Integration with Code Deployment

HTTP/NGINX configuration integrates with the code deployment system:

- **One-Time Setup**: NGINX configuration (`http-deploy`, `http-deploy-ssl`) is a one-time setup operation that happens after initial code deployment
- **Rarely Needs Changes**: Once configured, NGINX configuration rarely needs to be modified. You can continue deploying code updates without touching NGINX configuration
- **No NGINX Reconfiguration During Deployment**: Code deployments (`deploy` command) do not require NGINX configuration changes
- **Static File Serving**: NGINX continues serving static files from `/srv/{project_name}/site/` without any configuration changes needed for code redeployments
- **Flask Proxy**: NGINX continues proxying to Flask daemons on the same ports - no port changes occur during code deployments
- **Automatic Flask Restart**: File deployments automatically restart Flask daemons, but NGINX doesn't need restarting - it continues serving requests seamlessly
- **Configuration Independence**: NGINX configuration remains unchanged during code deployments - only application code files are updated
